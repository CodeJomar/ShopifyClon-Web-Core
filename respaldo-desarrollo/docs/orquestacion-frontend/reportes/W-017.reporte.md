## Decisiones tomadas
1. **Validación de código de plan en la API vs. Enunciado**:
   - El enunciado solicitaba probar con `PRUEBA_W017`. Sin embargo, la clase DTO en el backend (`CrearPlanRequest.java`, línea 15) valida estrictamente `@Pattern(regexp = "^[A-Z_]{3,30}$")`, la cual no incluye dígitos numéricos (`0-9`).
   - Por tanto, enviar cualquier código con dígitos resulta en `422 VAL-001` ("El código debe tener de 3 a 30 letras mayúsculas o guiones bajos").
   - Decisión: se probó la validación estricta con el formato exigido por la API usando el identificador `PRUEBA_W_DIECISIETE`, validando exitosamente el ciclo completo de creación, edición y retiro.
2. **FormPanel Footer**:
   - En todos los componentes modales (`PlanForm`, `EliminarPlanForm`, `SuspenderTiendaForm`), los botones de acción (`Cancelar`, `Guardar plan`, `Confirmar`, etc.) se pasan directamente como fragmento `<>...</>` en la propiedad `footer` de `FormPanel`, sin envolverlos en etiquetas `div` adicionales, en estricto cumplimiento con la regla de diseño.
