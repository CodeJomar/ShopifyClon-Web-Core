## Qué se hizo
- `comun/seguridad/IpClienteResolver.java` (nuevo, `@Component`): único componente que resuelve la "IP del cliente".
  - Usa `X-Forwarded-For` **solo** si `app.proxy.secreto` no está vacío, si `X-Proxy-Secreto` coincide y si el valor es una IP válida. En cualquier otro caso devuelve `getRemoteAddr()`.
  - Comparación del secreto: se compara la huella SHA-256 del valor esperado y del recibido con `MessageDigest.isEqual`, así que la longitud fija evita fugas por tiempo.
  - Validación de IP: IPv4 por expresión regular; IPv6 por reglas propias (grupos hexadecimales, un solo `::`, 8 grupos sin `::`). No se usa `InetAddress.getByName` para validar, porque con texto que no es IP puede consultar DNS.
  - No escribe nada en logs: ni el secreto ni la cabecera.
- `comun/seguridad/LimitePeticionesInterceptor.java`: usa `IpClienteResolver.ipDe(request)` en vez de `request.getRemoteAddr()`. Es el único uso de la IP del cliente en el código (búsqueda en `src/`); la auditoría no lee la IP.
- `src/main/resources/application.properties`: `app.proxy.secreto=${API_PROXY_SECRETO:}` (vacía por defecto). No se escribió ningún valor real.
- Pruebas nuevas:
  - `comun/seguridad/IpClienteResolverTest.java` (sin contexto Spring, 20 casos): secreto correcto usa la IP reenviada; secreto incorrecto, sin cabecera de secreto, secreto vacío, con la cabecera coincidente o secreto no configurado → IP de conexión; 11 valores que no son IP (texto, dominio, IPv4 fuera de rango, IPv4 incompleta, dos IPs separadas por coma, cadena vacía, IPv6 con `::` repetido, grupo de 5 dígitos, `:` inicial, 9 grupos) → IP de conexión; IPv4 e IPv6 válidas → se usan.
  - `comun/seguridad/LimiteIpProxyTest.java` (4 pruebas, con `app.proxy.secreto` configurado): con secreto correcto, dos IPs reenviadas distintas tienen límites independientes (30 POST → 201, el 31.º → 429 `GEN-429`; la otra IP sigue en 201); con secreto incorrecto, la IP reenviada se ignora (el 31.º con otra IP reenviada → 429); sin cabecera de secreto, igual (429); con secreto correcto pero `X-Forwarded-For` no válida (`no-es-ip-N`), se usa la conexión (429).
  - `comun/seguridad/LimiteIpSinSecretoTest.java` (1 prueba, `app.proxy.secreto=` vacío explícito): aunque llegue `X-Proxy-Secreto` vacío y `X-Forwarded-For` distinta, el 31.º POST desde la misma conexión → 429.

## Decisiones tomadas (no estaban en la tarea)
- **IPv6 con sufijo IPv4 embebido** (p. ej. `::ffff:203.0.113.7`) se rechaza y se usa la IP de la conexión. Es la opción conservadora: el contrato de la web envía una IP simple. Queda como límite conocido.
- **`X-Forwarded-For` con varias IPs** (una coma) se rechaza. El contrato dice "una sola IP"; no se toma la primera ni la última.
- **Sin resolución DNS**: la validación es solo sintáctica. Un nombre de host en la cabecera nunca genera una consulta de red.
- **Cabecera de secreto repetida**: se usa el primer valor que devuelve el servidor (`getHeader`). No se intentó tratar duplicados de forma especial.
- **Comparación de secreto**: SHA-256 de ambos lados + `MessageDigest.isEqual`. Con secreto vacío ni siquiera se calcula la huella (`huellaSecreto == null`), así que la cabecera no se evalúa.
- **Límites en memoria** (D-023): sin cambios. Con varias instancias el límite sigue siendo por instancia.
