1. El proyecto en una página

OTemu es una plataforma de tiendas en línea (estilo Shopify): un comerciante crea su tienda, publica productos y gestiona pedidos, pagos, envíos y rutas de reparto; un comprador compra en la vitrina pública. La parte que se evalúa es el backend (API REST); el frontend la consume.

2. Semana por semana: concepto → cómo lo tenemos → endpoint/archivo

Los temas salen del sílabo (Desarrollo Full Stack, 2026-2). Las semanas 1 a 8 son frontend; 9 a 14 son backend (lo que se evalúa en el APF2).

Unidad 1 · Introducción al Full Stack (semanas 1 y 2)

Sem. 1 · Full Stack y gestión de proyectos IMPLEMENTADO

Concepto

Full Stack = construir cliente (lo que ve el usuario) y servidor (reglas y datos) y conectarlos. Arquitectura cliente-servidor: el navegador pide, la API responde JSON por HTTP.

En el proyecto

Frontend Next.js (repo ShopifyClon-Web-Core) + backend Spring Boot (ShopifyClon-Api-Core). Gestión: tareas numeradas con documento y reporte por tarea (W-xxx frontend, A-/T- backend), tablero y ramas por tarea en GitHub.

Sem. 2 · Entorno, Git, contenedores y despliegue IMPLEMENTADO

Concepto

Git: control de versiones. Contenedor (Docker): empaqueta app + dependencias y corre igual en cualquier máquina; ligero porque comparte el kernel. Máquina virtual: simula un equipo completo con su propio sistema operativo (más pesada). Serverless: funciones que se ejecutan bajo demanda sin administrar servidor.

En el proyecto
  • Gitflow simple: ramas tarea/… y ajuste/… → develop (integración) → prod (despliegue automático). Commits con prefijo feat / fix / chore.
  • Docker: Dockerfile multi-etapa (compila con JDK, corre con JRE liviano) y docker-compose.yml con 3 servicios: shfy-api-core, shfy-web-core y shfy-stripe-cli, en un solo proyecto utp-desarrollo-shfy.
  • Nube: Railway despliega la API desde la rama prod; la base está en Supabase.
  • Serverless: no lo usamos. Vercel (serverless) no sirve para este backend: un Spring Boot es un proceso Java siempre encendido, no una función efímera.
P: ¿Por qué Docker y no instalar todo? R: Para que cualquier compañera levante el proyecto con un solo comando y el entorno sea idéntico al de producción.

Unidad 2 · Front-end (semanas 3 a 8)

Sem. 3 · Frameworks front-end, navegación y estado IMPLEMENTADO

Concepto

Un framework front-end organiza la interfaz en componentes, rutas y estado. Estado = datos que cambian y hacen que la pantalla se repinte.

En el proyecto

Next.js 16 (App Router) sobre React 19. Rutas por carpetas: /tienda/[subdominio] (vitrina), /panel/… (comerciante), /cuenta, /plataforma, /seguimiento. Estado global ligero con zustand (carrito, sesión). Código organizado por módulos en src/modules/*.

Sem. 4 · Bibliotecas de estilos y frameworks CSS IMPLEMENTADO

Tailwind CSS 4 (clases utilitarias) + componentes base tipo shadcn/ui (botón, tarjeta, alerta…) + iconos lucide. Tema claro/oscuro. Ventaja: consistencia visual y menos CSS propio.

Sem. 5 · Reactividad IMPLEMENTADO

Reactividad = cuando cambia un dato, la interfaz se actualiza sola. En React: useState/useEffect, y zustand para estado compartido. Ejemplo: al agregar al carrito, el contador del encabezado cambia sin recargar.

Sem. 6 · Consumo de APIs y formularios IMPLEMENTADO

axios para las solicitudes HTTP asíncronas; react-hook-form + zod para formularios con validación (el error de la API validaciones se muestra junto al campo). El navegador nunca habla directo con la API: pasa por un proxy de Next (/api/…) que reenvía y añade la sesión.

Sem. 7 · Autenticación en el front y despliegue del front IMPLEMENTADO

Sesión: el JWT se guarda en una cookie httpOnly (el JavaScript de la página no puede leerla, protege contra XSS) con sameSite=lax y secure en producción. La tienda activa y el token del carrito van también en cookies httpOnly.

Despliegue: Dockerfile del front en 3 etapas con salida standalone de Next (imagen mínima, usuario sin privilegios). Hoy solo el backend está en Railway.

Unidad 3 · Back-end (semanas 9 a 14)

Sem. 9 · Bases de datos relacionales, noSQL y Back-end como servicio IMPLEMENTADO

Concepto

Relacional (SQL): tablas con relaciones y garantías ACID; ideal para dinero, stock y pedidos. NoSQL: documentos/clave-valor sin esquema fijo; ideal para logs, cachés o datos muy variables. BaaS (Backend as a Service): un proveedor te da base, autenticación y almacenamiento ya montados.

En el proyecto
  • PostgreSQL alojado en Supabase. Elegimos relacional porque órdenes, pagos, stock y suscripciones necesitan integridad (una orden no puede existir sin su tienda; el stock no puede quedar negativo).
  • Construcción de la BD: migraciones Flyway versionadas: V1 esquema inicial, V2 suscripciones, V3 identidad, V4 pago pendiente de suscripción, V5 rutas y seguimiento, V6 seguridad (bloqueo, dos pasos, revocación de sesiones). Al arrancar, la API aplica lo que falte.
  • BaaS: usamos Supabase como Postgres gestionado y como Storage para las imágenes. La lógica y la seguridad siguen en nuestra API (no dependemos de las reglas de Supabase).
  • NoSQL: no lo usamos; se justificaría para auditoría/eventos masivos o catálogo en caché.
Dónde verlo

src/main/resources/db/migration/V1__esquema_inicial.sql · tablas como Tiendas, Productos, Variantes, Ordenes, Pagos, Envios, Rutas, Suscripciones, RegistroAuditoria.

Sem. 11 · Aplicaciones en tiempo real y WebSockets NO IMPLEMENTADO

Concepto

HTTP normal = el cliente pregunta y el servidor responde. WebSocket = una conexión abierta y bidireccional: el servidor puede empujar datos sin que el cliente pregunte (chat, notificaciones, estados en vivo). Se negocia con un handshake HTTP y luego se mantiene (ws:///wss://). En Spring: spring-boot-starter-websocket con STOMP sobre un broker simple.

Cómo está hoy

La dependencia spring-boot-starter-websocket está declarada en el pom.xml, pero no hay código de WebSocket. Lo más parecido a "tiempo real" que tenemos: webhook de Stripe (Stripe avisa al servidor), eventos internos asíncronos y la página de la orden que consulta cada 1,5 s hasta ver PAGADO (polling).

Si preguntan: "No lo implementamos en esta entrega; la dependencia está lista. El caso natural sería notificar en vivo al comerciante cuando entra o se paga una orden (/topic/tienda/{id}/ordenes) y al comprador el cambio de estado del envío. Hoy lo resolvemos con webhook + consulta periódica."

Sem. 12 · Autenticación y autorización IMPLEMENTADO

Concepto

Autenticación = ¿quién eres? (login). Autorización = ¿qué puedes hacer? (permisos).

En el proyecto
  • Autenticación: registro → código de 6 dígitos por correo → activación → login con correo y contraseña. Contraseñas con BCrypt (nunca en claro). Cuenta sin activar no entra (USR-003).
  • Autorización por roles y permisos: 4 roles de tienda con matriz fija en código — PROPIETARIO (todo), ADMINISTRADOR (todo menos suscripción), GESTOR_CATALOGO (catálogo e inventario), GESTOR_PEDIDOS (ver/gestionar/cancelar órdenes). 12 permisos (p. ej. CATALOGO_GESTIONAR, REEMBOLSOS_EMITIR). Cada endpoint del panel declara @RequierePermiso(...).
  • Administrador de plataforma: rol global (@SoloAdministradorPlataforma) para planes y suspensión de tiendas.
  • Aislamiento entre tiendas con X-Tienda-Id (404 si no eres miembro).
  • Más defensas: límite de peticiones por minuto por IP del visitante (429) en login, registro, carrito, checkout y pagos; validación de entradas; auditoría de acciones sensibles.
  • Bloqueo por fuerza bruta: 5 contraseñas incorrectas seguidas bloquean esa cuenta 15 minutos (409 USR-014). El dueño recibe un correo con un código y la desbloquea en POST /auth/desbloquear, así nadie puede dejarlo fuera a propósito.
  • Contraseñas: 8 a 72 caracteres con letra y número; se rechazan las más comunes (Password123…) y las que contienen el correo (USR-015).
  • Revocación de sesiones: cambiar o restablecer la contraseña invalida todos los tokens emitidos; también POST /cuenta/cerrar-sesiones.

Sem. 13 · JSON Web Token (JWS) y seguridad en dos pasos IMPLEMENTADO

Concepto JWT

Un JWT son 3 partes en base64 separadas por puntos: header (algoritmo) · payload (claims: quién, cuándo vence) · firma. Si está firmado se llama JWS (JSON Web Signature): cualquiera puede leerlo, pero nadie puede modificarlo sin romper la firma. Es stateless: el servidor no guarda sesiones.

En el proyecto (JWT)
  • Librería JJWT. Firma HMAC-SHA (HS256 o mayor según el tamaño de la clave) con el secreto JWT_SECRET_KEY (variable de entorno, nunca en el código).
  • Claims: sub = UUID del usuario, correo, iat (emisión) y exp = 24 horas.
  • Flujo: POST /auth/login devuelve token → el cliente lo manda en Authorization: Bearer … → el filtro JwtFiltroAutenticacion lo valida y comprueba que el usuario siga existiendo y activo.
  • Revocación sin lista negra: el usuario guarda la fecha SesionesValidasDesde; un token emitido antes de esa fecha se rechaza (401). Se actualiza al cambiar la contraseña o al cerrar sesiones. Así un token robado deja de servir.
Concepto 2FA

Autenticación en dos pasos / dos factores (2FA): combinar dos pruebas distintas, algo que sabes (la contraseña) y algo que tienes (acceso a tu correo o a tu teléfono). Aunque roben la contraseña, no entran sin el segundo factor.

En el proyecto (dos pasos por correo, opcional por usuario)
#EndpointQué pasa
0PUT /cuenta/dos-pasosEl usuario lo activa con {activo: true, contrasena_actual}. El perfil muestra dos_pasos_activo. Por defecto está apagado.
1POST /auth/loginCorreo y contraseña correctos → no entrega token: responde requiere_segundo_factor: true y envía un código de 6 dígitos al correo.
2POST /auth/login/verificar{correo_electronico, codigo} → ahora sí llega el token.
  • El código es de un solo uso, vence en 10 minutos, admite 5 intentos y se guarda como hash SHA-256 (nunca en claro). Solo se emite después de una contraseña correcta.
  • Los mismos códigos de un solo uso protegen la activación de la cuenta, la recuperación de contraseña y el desbloqueo.
  • Se pide solo al iniciar sesión; después el token vale 24 horas.
Si preguntan «¿es 2FA de verdad?»: "Sí: contraseña más un código de un solo uso enviado al correo. Es verificación en dos pasos por correo; el nivel siguiente sería TOTP con una app autenticadora (Google Authenticator) o una llave física, que no implementamos."
Si preguntan «¿por qué es opcional?»: "Para no obligar a todos los compradores; el comerciante o el administrador pueden activarlo en su cuenta. Se podría forzar para el rol de administrador de plataforma."

Unidad 4 · Integración, despliegue y monitoreo (semanas 15 a 18)

Integración cliente-servidor IMPLEMENTADO

Auditoría en base de datos (RegistroAuditoria) de acciones sensibles (cambios de rol, cancelaciones, pagos tardíos). No hay Prometheus/Grafana.

6. Preguntas probables del docente

¿Cómo se protege la API? JWT firmado (24 h) y revocable, contraseñas con BCrypt y rechazo de las comunes, verificación en dos pasos opcional, bloqueo de la cuenta tras 5 fallos, roles y permisos por endpoint (@RequierePermiso), aislamiento por tienda (X-Tienda-Id), límite de peticiones por IP, CORS con lista de orígenes, cabeceras de seguridad (HSTS, nosniff, X-Frame-Options), validación de entradas y firma verificada en el webhook de Stripe.
¿Qué pasa si me roban el token? Sirve como máximo 24 horas, y deja de servir en cuanto cambio la contraseña o uso «cerrar sesiones»: el servidor rechaza los tokens emitidos antes de esa fecha.
¿Y un ataque de fuerza bruta al login? Dos barreras: 10 intentos por minuto por IP (429) y, si usan muchas IP, la cuenta se bloquea 15 minutos tras 5 fallos (USR-014) y se avisa al dueño por correo con un código para desbloquearla.
¿Qué es CORS y cómo lo tienen? Es la regla del navegador que decide qué sitios web pueden llamar a la API. Solo aceptamos los orígenes de una lista (CORS_ORIGENES_PERMITIDOS); cualquier otro recibe 403.
¿Qué es un JWT y por qué no hay sesión en el servidor? Un token firmado con la identidad del usuario y su vencimiento. El servidor solo verifica la firma (y que el usuario siga activo), no guarda sesiones: la API escala sin estado compartido.
¿Dónde guardan el token en el frontend? En cookie httpOnly (JavaScript no la lee, mitiga XSS), sameSite=lax y secure en producción; un proxy de Next la convierte en Authorization: Bearer.
¿Qué pasa si dos personas compran el último producto a la vez? El stock se reserva al crear la orden con bloqueo en base de datos; el segundo recibe INV-002. Hay prueba de concurrencia. Se descuenta al confirmar el pago y se libera si la orden vence.
¿Qué es la idempotencia y para qué el Idempotency-Key? Repetir la misma petición no repite el efecto: si el comprador hace doble clic en "Confirmar", se devuelve la misma orden en vez de crear dos.
¿Por qué el webhook de Stripe y no confiar en el navegador? El navegador puede mentir o cerrarse. Stripe avisa servidor a servidor con una firma que verificamos; solo entonces la orden pasa a PAGADO.
¿Cómo se evita que una tienda vea datos de otra? Cada consulta del panel filtra por la tienda de la cabecera y se valida que el usuario sea miembro; si no, 404.
¿Qué arquitectura usa el backend? Por capas (controlador, servicio, repositorio, entidad) más DTO y mapeador; un test de ArchUnit impide saltarse capas. Modular por contexto de negocio.
¿Cómo versionan la base de datos? Con Flyway: scripts V1…V6 que se aplican en orden al arrancar; nadie toca la base a mano.
¿Cómo prueban? Pruebas de integración contra PostgreSQL real (Testcontainers), pruebas de arquitectura (ArchUnit), pruebas unitarias y e2e del frontend (Playwright). Además el laboratorio de endpoints ejecuta ~370 casos contra la API.
¿Qué hace el eliminar? ¿Borra de verdad? Eliminación lógica: marca el registro como eliminado, así no se rompen órdenes históricas.
¿Cómo se despliega? Push a la rama prod → Railway construye el Dockerfile, valida /health y publica. Secretos solo en variables de entorno.
¿Qué pasa si falla el correo o Stripe? El envío de correo es asíncrono y su fallo no rompe el registro (se registra en el log); los webhooks de Stripe se reintentan y son idempotentes.
¿Cómo calculan los totales? Solo el servidor: nunca se confía en montos del cliente; el cliente envía total_esperado y la API lo compara con su cálculo (CHK-004 si difiere).
¿Cómo manejan los errores? Excepciones de negocio con código (INV-002, SUS-017…) y un manejador global que arma el sobre estándar con HTTP correcto: 400, 401, 403, 404, 409, 422 y 429.

7. Guion de demostración (10 minutos)

Usar el laboratorio en Railway: …/api/v1/laboratorio/index.html. Cada paso es un botón; lo que se genera se guarda y lo usa el siguiente.

1
Cuenta y sesión → Registro (llega el código al correo) → Activar → Login. Mostrar el token y explicar el JWT. Mostrar un 401 sin sesión. Seguridad: «Verificación en dos pasos» (activar → login sin token → canjear el código del correo), «Provocar el bloqueo (5 fallos)» y «Cerrar todas mis sesiones». Los correos pueden caer en spam.
2
Tienda y personal → «Crear una tienda de prueba». Mostrar la configuración, la vitrina pública y un 404 al usar el X-Tienda-Id de otra tienda (aislamiento).
3
Suscripción → ver estado PRUEBA, pagar con tok_lab; mostrar tok_rechazar (rechazo). Explicar SUS-017.
4
Tarifas → crear tarifa. Catálogo → «Crear producto publicado»; probar el caso de publicar sin imagen (CAT-007). Cupones → crear uno.
5
Carrito → crear carrito, agregar 2 unidades, aplicar cupón, cotizar con envío. Checkout → probar error CHK-004 y ENV-007, luego «Compra exitosa». Explicar reserva de stock e idempotencia.
6
Pagos → pago manual y ver PAGADO; mostrar reembolso parcial. (Opcional en el frontend: pagar con tarjeta 4242 y ver el webhook.)
7
Envíos y Rutas → preparar (guía), crear ruta, iniciar, «no entregado», entregar, finalizar. Seguimiento → consultar la guía sin sesión.
8
Métricas y Swagger. Cierre: mostrar /health, el Dockerfile, docker compose y el despliegue de Railway.

Atajos útiles

  • Receta «Todo de una vez» (en Envíos/Órdenes): crea tienda, tarifa, producto, carrito, orden pagada y envío en un clic.
  • «Ejecutar todo el módulo» corre todos los casos del módulo y muestra ✔/✘ (se omiten los casos manuales).
  • Si da 429 el laboratorio espera y reintenta solo. Si da SUS-017, la tienda está vencida: usar «Crear una tienda de prueba».
